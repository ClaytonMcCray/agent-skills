# Zircon C++ to Rust port: the doctrine

This is a line-by-line, bug-for-bug, comment-for-comment port. The Rust is meant to look like the C++, not like good Rust. That is deliberate: it makes review mechanical, and the kernel gets cleaned up in a later phase.

1. **Structure parity.** Same file split as the C++ unless the tree's existing ports of the same kind split differently, same order of declarations and functions, same statement order inside functions, same early returns, same loops, same helper decomposition. Do not merge, split, reorder, inline, or extract anything the C++ did not.
2. **Behavior parity, including bugs.** Port every behavior the C++ has, including races, off-by-ones, missing checks, and questionable orderings. Do not fix them. When you find one, port it faithfully and list it in your report under "C++ bugs ported as-is" with `cpp path:line`, so a bug gets filed. Do not add TODO comments without a bug number.
3. **Comment parity.** Every comment in the C++ body and header that documents behavior appears in the Rust at the same place, with identifiers adapted to the Rust names. Doc comments become `///`. Adapt, never drop, never "improve". Rename rules the port uses:
   - methods and functions: `DoThing()` becomes `do_thing()`; `ClassName::Method` becomes `ClassName::method`
   - fields: `count_` becomes `count`; constants: `kMaxSize` becomes `MAX_SIZE`; macros keep their names
   - `nullptr` becomes `None` or a null pointer, whichever the Rust uses; `ZX_ERR_NO_MEMORY` becomes `Status::NO_MEMORY`; `fbl::RefPtr<T>` becomes `RefPtr<T>`; `ktl::move` becomes a move; `TA_REQ(lock_)` becomes the `LockToken` parameter
   - a comment that names a C++ construct with no Rust counterpart (`this`, a destructor, an `override`) is rewritten to name the Rust counterpart (`self`, `Drop`, the trait impl)
4. **Unsafe is expected.** Raw pointers, unsafe blocks, and manual lifetime handling that mirror the C++ are correct at this phase. Every `unsafe` block gets a `// SAFETY:` comment stating the C++ invariant it relies on; every `unsafe fn` gets a `# Safety` section. Do not restructure code to avoid unsafe.
5. **Safety surface parity, not safety improvement.** The port must not introduce Rust-specific undefined behavior the C++ did not have: no aliased `&mut`, no references to uninitialized or misaligned memory, no data races through plain references (use atomics, raw pointers, or `UnsafeCell` where the C++ raced), no invalid enum discriminants, no unchecked integer overflow where the C++ wrapped (`wrapping_*`), no panics on paths where the C++ continued. Where the C++ was unsound, the Rust reproduces the observable behavior in a way Rust defines. Tree-wide guidance: `docs/development/languages/rust/unsafe.md`.
6. **The port's machinery is mandatory**, because it is how parity is expressed in this kernel, not a style choice: `zr::static_assert_size_and_align!` for layout; `kalloc` for fallible allocation and never a panic on OOM; `ksync` tokens and `#[guarded]` matching the C++ thread-safety annotations and lock policies (IRQ-saving or not); `fbl` intrusive containers and `RefPtr`; `ltrace` for `LTRACE`; `zx_status::Status`; `zr::defer` for `fit::defer`; `LazyInit` for bare globals; `unittest` suites for kernel tests; `cpp_` and `rust_` FFI naming, with `FFI_ALWAYS_INLINE` and the TODO for https://fxbug.dev/537458631 on short C++ shims; assertion parity (`ASSERT` to `assert!`, `DEBUG_ASSERT` to `debug_assert!`); canary parity; allocation-tier parity; copyright preservation. Each applies where the C++ has the corresponding construct: `LazyInit` for globals the C++ initialized dynamically, while a constant-initialized C++ static stays a plain `static`; layout asserts for types that cross FFI or replace C++ object storage, not for Rust-private types; canaries and traces only where the C++ had them.
7. **Rubric precedence.** `zircon/skills/cpp-to-rust-rubric/SKILL.md` is the team's shared rubric and every role reads it. Where it asks for parity or for the machinery above, it binds. Where it asks for idiom, it is deferred to the cleanup phase: Core Principle 8 (ergonomic design and DRY), Pitfall 13 (derivable traits), the reviewer instruction to "insist on safe Rust alternatives", and any advice to restructure for idiom. A parity reviewer treats an idiomatic improvement as a defect at this phase. `.agents/skills/rust_best_practices` does not apply to this phase.
8. **Tests port too**, test by test, with the same assertions, under the suite-naming rules in the rubric (append `_rust` on a name collision, never prefix `rust_`), in `#[cfg(ktest)]` `unittest` suites for kernel code, run with `k ut <suite>`. Additional Rust tests beyond the C++ set are allowed, since the rubric asks for equal or greater coverage; they are not a parity defect. A `_rust` suite suffix is only for a name collision with an existing C++ suite.
